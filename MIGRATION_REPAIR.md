# Переход существующей БД master на develop без пересоздания

Этот пакет исправляет запуск develop на БД со следующей подтверждённой историей. Существующие записи истории и исходные таблицы не удаляются.

```text
20250719070930_Init
20250725153627_Act1
20260925183255_AddDocumentVersioning
```

## Почему возникла ошибка

Начальная миграция develop `20261023213643_Init` отличается от начальной миграции master. База уже содержит Identity-таблицы, но в её истории нет develop Init, поэтому прежний Startup пытался повторно создать AspNetRoles.

Присланный пользователем `AddDocumentVersioning.cs` также расходится со своим Designer: реальный Up создаёт timestamp without time zone, удаляет UserReferencesInMinio и не добавляет поля статусов или FK CurrentVersionId, хотя Designer описывает другую схему. Исправление опирается на фактический Up и предоставленную структуру БД, а не только на Designer.

## Порядок действий

### Подготовка и резервная копия

1. Остановите приложение в Visual Studio и все другие экземпляры API, которые используют эту БД.
2. Создайте полную резервную копию PostgreSQL. Например, в pgAdmin: правая кнопка по нужной БД, Backup, формат Custom; не включайте режим Only schema, нужны и схема, и данные.
3. Предпочтительно восстановите копию в отдельную БД и сначала проверьте переход на ней. Само наличие файла backup не заменяет проверку восстановления.
4. Сохраните используемые настройки подключения; скрипт нужно выполнять в той же БД, куда подключается HTTP-профиль приложения.
5. Не удаляйте таблицы, историю миграций и Docker volumes. Не запускайте `Update-Database 0`, `EnsureDeleted`, `docker compose down -v`.

Скрипт не обращается к MinIO и не изменяет его объекты. Его существующие файлы также следует сохранять обычным способом резервного копирования хранилища.

### Предварительная проверка

Откройте Query Tool в pgAdmin для нужной БД. Откройте и выполните целиком `scripts/preflight_legacy_database.sql`, сохраните вывод с количеством записей и примерами дат.

На этом этапе выполняются только SELECT. В результате должны быть видны указанные выше три миграции и таблицы Documents / DocumentVersions.

### Подтверждённый часовой пояс старых дат

В `scripts/repair_legacy_database.sql` есть строка:

```sql
SELECT set_config('newtpt.legacy_timestamp_zone', 'Europe/Samara', true);
```

Пользователь подтвердил `Europe/Samara` и сообщил, что пояс PostgreSQL с сентября не менялся. В поставляемом скрипте значение уже установлено, менять его не нужно.

Для понимания преобразования:

- **UTC**: если старое `2026-02-03 12:34:56` означает именно 12:34:56 UTC, укажите `UTC`.
- **Europe/Samara**: если то же старое значение означает самарское местное время, укажите `Europe/Samara`; результат соответствует 08:34:56 UTC.
- **Другой пояс**: укажите соответствующее полное имя из PostgreSQL `pg_timezone_names`.

Нельзя выбрать пояс только по месту проживания пользователя. В исходной миграции даты создавались через NOW() с записью в timestamp without time zone: для таких записей нужен TimeZone сеанса, в котором выполнялась миграция; последующие записи приложения могли иметь свои правила.

`SHOW TimeZone` показывает только текущую настройку соединения и само по себе не доказывает исторический пояс. Если источники дат использовали разные пояса, этот общий скрипт применять нельзя: потребуется отдельное правило преобразования по группам записей.

Эта версия подготовлена для подтверждённого `Europe/Samara`. Например, старое значение `2026-09-25 22:49:57.453348` соответствует `2026-09-25 18:49:57.453348 UTC`; отображение через соединение Europe/Samara остаётся `22:49:57.453348+04`.

### Выполнение перехода

1. В pgAdmin откройте `scripts/repair_legacy_database.sql`.
2. Убедитесь, что в указанной строке уже стоит `Europe/Samara`; дополнительных замен не требуется.
3. Выполните весь файл целиком, не выделяя отдельные операторы.
4. Дождитесь успешного COMMIT и вывода истории. Сообщения об удалении объектов служебной схемы `newtpt_expected_baseline` относятся только к созданному скриптом эталону, не к вашим таблицам.
5. Если возникла ошибка, не запускайте дальнейшие фрагменты. Выполните `ROLLBACK;` в том же Query Tool, сохраните полный текст ошибки и разберите причину.

Скрипт использует одну транзакцию, блокировки исходных таблиц и тайм-ауты. Он предназначен для окна обслуживания с остановленным API; на большой БД время и длительность блокировок нужно предварительно оценить на восстановленной копии.

### Обновление файлов и запуск

Скопируйте исходники из нового полного архива либо примените небольшой архив исправления к ранее переданному develop. Список файлов малого исправления приведён в `PATCH_FILES.md` внутри малого архива; прежние файлы миграций develop не удаляются и не переименовываются.

После скрипта запустите приложение в Visual Studio в HTTP-профиле с подключением к проверенной БД. Startup пропустит согласованную Init и применит обычную миграцию ChunkUploads.

Ожидаемая история после этого:

```text
20250719070930_Init
20250725153627_Act1
20260925183255_AddDocumentVersioning
20261023213643_Init
20261030151648_ChunkUploads
```

Новая защита в Startup не выполняет согласование скрытно: если legacy-база ещё не подготовлена, она выдаёт сообщение со ссылкой на эту инструкцию. Отключение Database:ApplyMigrations не исправляет недостающие столбцы и таблицы.

## Какие изменения делает скрипт

- **Даты документов и версий**: переводит три столбца timestamp without time zone в timestamptz через явное `AT TIME ZONE`. Идентификаторы и остальные значения документов/версий сохраняются.
- **Статусы**: добавляет FileName и FileExtension, заполняет их из одноимённых camelCase/PascalCase ключей JSON; при отсутствии ключа использует пустую строку. Исходный StatusParams не изменяется.
- **Legacy-ссылки**: если UserReferencesInMinio отсутствует, создаёт таблицу и восстанавливает одну ссылку на каждую существующую версию. Эти строки получают новые Id, поскольку старая таблица уже удалена исторической миграцией; старые Id восстановить из документов нельзя.
- **CurrentVersionId**: проверяет, что текущая версия существует и принадлежит тому же документу, добавляет отсутствующие FK и индекс. При неверных ссылках не угадывает исправление, а отменяет транзакцию.
- **UserProfilesMinio**: не удаляет и не изменяет эту legacy-таблицу.
- **Контроль схемы**: внутри транзакции создаёт отдельный эталон из SQL develop Init, сравнивает все его столбцы, типы, nullable, identity, PK/FK и индексы с public. Дополнительная legacy-таблица UserProfilesMinio допустима.
- **История**: только после успешных проверок добавляет отметку develop Init, не выполняя её DDL на ваших Identity-таблицах. Исходные три строки остаются.
- **Повтор**: не создаёт повторные ссылки, не сдвигает даты повторно и не добавляет дубликат истории. Повтор с другой неизвестной историей отклоняется.

Если в БД есть неожиданные отличия, скрипт откатится. Это намеренная защита, а не повод отключать проверки или выполнять INSERT истории отдельно.

## Проверки

На реальном PostgreSQL воспроизведены исходная Init master, пустая Act1 и присланная AddDocumentVersioning. В тестовую БД внесены пользователь с контрольным PasswordHash, роль/связь роли, профиль MinIO, документ/версия и JSON-статусы.

Девять специальных тестов проверяют сохранение этих данных, первоначальную ошибку 42P07, защиту Startup, выбор часового пояса, повторный запуск, применение ChunkUploads и откат при неверной схеме, FK, индексе, истории или CurrentVersionId. Проверки выполнены только на отдельных тестовых БД; ваша локальная БД из этой сессии не изменялась.

Подробности полного прогона находятся в `TEST_REPORT.md`, машинные результаты в `TestResults/legacy-migrations.trx` и `TestResults/all-tests.trx`. Новые интеграционные тесты создают и удаляют только свои базы с префиксом `newtpt_legacy_test_`; для них нужна тестовая PostgreSQL-роль с правом CREATEDB, без необходимости выдавать это право рабочему API.

После перехода сравните количество пользователей/ролей/документов/версий/статусов и проверьте скачивание старого документа через приложение. Тестовое воспроизведение не заменяет проверку резервной копии и данных вашей конкретной БД.

## Ограничение отката миграций

Это согласование существующей схемы с baseline develop, не переписывание прошлой истории. Нельзя после него без отдельного плана выполнять downgrade до состояния ниже develop Init: её Down предназначен для базы, созданной этой Init, и может удалить существующие таблицы.

Если после COMMIT требуется отменить переход, используйте заранее проверенную резервную копию либо отдельно подготовленный обратный план. Не удаляйте отметку Init вручную.

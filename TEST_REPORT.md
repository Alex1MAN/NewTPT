# Проверка NewTPT develop

Проверка выполнена 30 октября 2026 года на изменённом исходном коде из приложенных архивов с последующим исправлением перехода legacy-БД. Итог обновлённого прогона: Release-сборка успешна, все 61 xUnit-тест пройдены, пропусков нет.

## Среда и сборка

- **SDK**: .NET SDK 7.0.410, целевая платформа net7.0, Linux x64.
- **PostgreSQL**: реальный Docker-контейнер PostgreSQL 16.15, не EF InMemory и не SQLite.
- **MinIO**: реальный S3-сервер в Docker, собранный Go 1.21.6 из исходного тега `RELEASE.2024-01-18T22-51-28Z`. Строка версии самостоятельно собранного бинарника: `DEVELOPMENT.GOGET`.
- **API**: опубликованное Release-приложение запущено в контейнере `mcr.microsoft.com/dotnet/aspnet:7.0`; интеграционные запросы проходят через настоящий Kestrel.
- **Сборка**: `dotnet build JWTAuthTemplate/JWTAuthTemplate.csproj -c Release -t:Rebuild`, 0 ошибок, 22 предупреждения. В исходном develop до изменений было также 22 предупреждения; общая очистка старых nullable/unused warnings не входила в перенос.
- **Compose**: конфигурация успешно проходит `docker compose ... config --quiet`.

Полная многостадийная Docker-сборка через исходный SDK-Dockerfile не завершилась в этой среде из-за лимита диска и storage-driver vfs. Поэтому для фактических контейнерных тестов использованы `dotnet publish` и `docker/runtime.Dockerfile`; MinIO аналогично собран из исходников снаружи Docker и упакован `docker/minio-runtime.Dockerfile`.

Контейнеры проверялись с `--network host`: обычная bridge-сеть Docker и запуск из интерфейса Visual Studio здесь не проверялись. Не следует трактовать успешные интеграционные тесты как выполненный Windows/Visual Studio smoke-test или успешный полный `docker compose up --build`.

## Чанки и сохранение данных

- **Порядок и конкуренция**: части файла объёмом `11 MiB + 31 байт` отправлены параллельно и не по порядку; сборка проходит через multipart-механику MinIO SDK.
- **Целостность**: SHA-256 исходного массива совпадает с SHA-256 скачанного файла.
- **Идемпотентность**: два параллельных CompleteUpload возвращают один DocumentId; прямые SQL-проверки подтверждают ровно один Document, одну DocumentVersion и одну legacy-ссылку.
- **Повторы**: одинаковая часть принимается повторно; другая часть с тем же индексом даёт 409.
- **Пропуски**: незавершённый набор не фиксирует документ; после досылки отсутствующей части завершение успешно.
- **Ошибки**: неизвестная сессия даёт 404; неверные индексы, размеры, имена-пути и метаданные отклоняются; чрезмерное HTTP-тело не получает OK.
- **Повреждение**: модульная подмена байтов сохранённого чанка выявляется SHA-256 до фиксации документа.
- **Сбои хранилища**: модульно проверены отсутствие Commit при отказе Put и сохранение квитанции при отказе уборки.
- **Уборка**: интеграционный запрос к MinIO подтверждает отсутствие временной части после завершения.
- **Перезапуск процесса**: дополнительно выполнен `scripts/restart_smoke.py`; контейнер API перезапущен между отправкой частей и CompleteUpload, файл собран правильно, повторное завершение вернуло тот же DocumentId.

Максимальный файл 10 GiB, длительный нагрузочный прогон, аварийное завершение PostgreSQL/MinIO и сетевые partition-сценарии не проверялись. Состояние и блокировки проверены в реальном PostgreSQL, а не только в mock-репозитории.

## Независимая проверка PCA

Выполнены HTTP-запросы `AnalyzeExcel` к финальному контейнеру с обоими исходными Excel-файлами. Все доли объяснённой дисперсии сравнены с независимым NumPy `eigvalsh`, с population-стандартизацией и делителем covariance `n-1`.

| Файл | Полных числовых строк | Непустых столбцов | Максимальная абсолютная ошибка доли дисперсии |
|---|---:|---:|---:|
| NiCu100.xlsx | 100 | 741 | 2.9976021664879227e-15 |
| NiCu1000.xlsx | 1002 | 741 | 2.142730437526552e-14 |

Порог сравнения: `1e-10`; оба файла прошли. Количество строк указано по фактическому правилу чтения TestPCA, а не выведено из имени файла; Excel-метаданные содержат также форматированные пустые столбцы, не входящие в анализ.

Дополнительно проверены аналитический случай двух полностью коррелированных признаков, ортогональная реконструкция scores × loadingsᵀ, совпадение Transform обучающих данных со Scores и строго нулевой результат стандартизации постоянного десятичного столбца.

## Миграция и регрессии

- **Свежая база**: API успешно применил Init и новую ChunkUploads.
- **Upgrade**: отдельно создана база на уровне Init, добавлена контрольная запись 42, затем применена ChunkUploads; запись сохранилась, обе миграции зарегистрированы.
- **Версионирование**: сохранены загрузка первой версии, создание второй, удаление версии и удаление документа.
- **Исправленный дефект develop**: DeleteDocumentAsync раньше выдавал 500 из-за цикла CurrentVersionId/DocumentId; теперь ссылка снимается и документ удаляется внутри одной транзакции.
- **Дополнительные исправления**: получение текущего пользователя в SessionService, срок refresh token при Authenticate, необязательный Id при операциях с RoleDTO, правильный presigned URL вместо содержимого файла.

Парсер реального бинарного SPC не проверен на эталонном SPC: таких файлов среди исходных архивов не обнаружено. Его готовая DLL не переписывалась; агрегация нескольких результатов и dispatch по расширению проверены модульно.

## Исправление перехода с фактической legacy-истории

После первоначального пакета пользователь предоставил историю старых миграций и отсутствовавшую в исходном master миграцию AddDocumentVersioning. Она создаёт timestamp without time zone, удаляет UserReferencesInMinio и не создаёт описанные в Designer столбцы статусов/FK CurrentVersionId; воспроизведён именно её фактический Up.

Вместо удаления базы или слепого INSERT истории добавлены `MIGRATION_REPAIR.md`, транзакционный SQL со сравнением структуры с эталоном develop Init и защита `DatabaseMigrationRunner` в Startup. Исторические файлы миграций develop не изменены; три исходные записи истории сохраняются.

На девяти отдельных сценариях PostgreSQL проверены:

- **Полный переход**: исходная ошибка 42P07 воспроизведена; после скрипта и штатной ChunkUploads база читается через актуальный Context.
- **Сохранение**: точное совпадение JSON-снимков пользователей с PasswordHash, ролей, связей ролей, профилей, неизменяемых полей документов/версий и исходных статусов до/после перехода.
- **Даты**: сохранена микросекундная точность; Europe/Samara переводится в правильный UTC-момент, явный UTC не зависит от TimeZone подключения America/New_York.
- **Повторы**: повтор до/после ChunkUploads не дублирует данные и не сдвигает даты.
- **Отказы**: отсутствие подтверждённого пояса, неверный тип столбца, отсутствующий FK, индекс без требуемого UNIQUE, неизвестная история и неверный CurrentVersionId приводят к отмене.
- **Новая база**: штатные Init/ChunkUploads по-прежнему применяются; legacy-скрипт отказывается работать на базе без ожидаемой истории.

Никаких операций на локальной БД пользователя не выполнялось. Скрипт требует резервную копию и остановленный API; в текущей версии уже задан подтверждённый пользователем `Europe/Samara`, дополнительная замена значения не нужна. Основной тест перехода запускает именно поставляемый скрипт без подмены пояса; отрицательная проверка явно подставляет невалидный CHANGE_ME.
